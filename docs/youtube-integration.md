# Интеграция с YouTube Data API v3

## Архитектура

Интеграция изолирована в пакете `internal/youtube` и подключена к домену через `youtube.Adapter`, реализующий `youtube.VideoPublisher`:

- `internal/youtube/oauth.go` — OAuth 2.0 Authorization Code + PKCE, loopback callback, `persistingTokenSource` (атомарное сохранение обновлённых токенов без потери `refresh_token`).
- `internal/youtube/tokenstore.go` — файловое хранилище токена с правами `0600` и запретом хранения внутри git working tree (включая проверку симлинков).
- `internal/youtube/journal.go` — локальный журнал операций (`uploads.json`) с атомарной записью и межпроцессной блокировкой (`flock`) по файлу журнала и по каждому `IdempotencyKey`.
- `internal/youtube/resumable.go` — resumable upload (`videos.insert`), проверка прогресса (`308 Resume Incomplete`), восстановление после разрыва/сбоя и опрос обработки (`WaitProcessing`).
- `internal/youtube/client.go` — клиент Data API v3 (`GetChannel`, `VerifyChannel`, `GetVideo`, `GetProcessingStatus`, `SchedulePublication`), backoff с jitter и поддержкой `Retry-After`.
- `internal/youtube/adapter.go` — адаптер `VideoPublisher`, сохраняющий `VideoJobID` и `IdempotencyKey` между `Upload` и `Schedule`.

## Защита от дубликатов и семантика idempotency key

YouTube Data API `videos.insert` не гарантирует идемпотентность по произвольному клиентскому ключу, поэтому каждый вызов `UploadVideo` обязан использовать `Journal`:

- Для одного `IdempotencyKey` берётся эксклюзивная блокировка `AcquireKey` (`flock`) на время всей операции.
- При повторном вызове для уже завершённой (`COMPLETED`) операции: если локальный исходный файл всё ещё существует, проверяется совпадение размера и SHA-256 (использование того же ключа для другого файла отклоняется); если исходный файл уже удалён, возвращается сохранённый результат (`Resumed: true`) без повторной загрузки и без создания дубликата.
- При возобновлении незавершённой операции проверяется совпадение размера и SHA-256 содержимого файла: повторное использование того же ключа для другого файла отклоняется.
- Повреждённый, пустой, усечённый или неподдерживаемой версии файл журнала завершается с ошибкой (fail-closed) и не перезаписывается.
- В CLI (`cmd/cli/youtube.go`) ключ по умолчанию вычисляется как SHA-256 от **содержимого файла** и нормализованного `--title`, поэтому относительный/абсолютный путь и изменение `mtime` не создают дублей.

## Состояние `UNKNOWN` и ручное восстановление

При неоднозначном исходе (например, сетевой обрыв, `503` при `querySession`, потеря сессии `404`/`410`, сбой до сохранения `SessionURI` или отмена контекста после начала сессии):

1. Клиент запрашивает статус существующей `SessionURI` (`Content-Range: bytes */<total>`).
2. Если сервер вернул `200`/`201`, операция завершается и сохраняется `VideoID`.
3. Если сервер вернул `308`, загрузка продолжается с подтверждённого смещения `Range` (с соблюдением `Retry-After`, если он передан).
4. Если определить исход невозможно (включая `404`/`410` или отсутствие `SessionURI`), запись переводится в терминальное состояние `UNKNOWN` с сохранением `SessionURI` и `SentBytes`; автоматическая повторная загрузка (`videos.insert`) **никогда не запускается**, даже при последующих повторах с тем же ключом.
5. Если при последующем вызове для `UNKNOWN` с сохранённым `SessionURI` `querySession` подтвердит `200`/`201`, клиент завершит запись и вернёт `VideoID` без создания новой сессии.

Для ручного восстановления после `UNKNOWN` / `FAILED`:
- Проверьте список записей: `go run ./cmd/cli youtube uploads` (чувствительные параметры URL в сообщениях об ошибках редактируются).
- **Обязательно** проверьте в YouTube Studio, появилось ли видео на канале, прежде чем предпринимать какие-либо действия.
- Удаление записи из журнала или смена `--idempotency-key` допустимы **только** после того, как вы вручную убедились в YouTube Studio, что видео действительно не было создано; в противном случае это приведёт к дубликату на канале.

## Назначение публикации (`SchedulePublication`)

- Все внутренние расчёты и хранение выполняются в **UTC**; CLI `--publish-at` принимает RFC3339 или локальное время `Europe/Moscow` (`YYYY-MM-DD HH:MM`).
- По умолчанию `youtube schedule` работает в режиме **dry-run** и не отправляет `PUT /videos?part=status`; фактическое обновление требует `--confirm-schedule`.
- В запросе передаётся `status.privacyStatus=private` и `status.publishAt` в будущем, с сохранением текущих `license`, `embeddable`, `publicStatsViewable` и `selfDeclaredMadeForKids`.
- `Adapter.Schedule` предварительно проверяет связь публикации в журнале (`VideoJobID`, `IdempotencyKey`) до отправки `PUT` и отклоняет неизвестную публикацию или публикацию, локально известную как `public`.
- **Ограничение API:** `videos.list` возвращает только текущий `privacyStatus` и **не содержит истории прошлых публикаций**. Поэтому ни проверка `privacyStatus == "private"`, ни `dry-run` не доказывают, что видео никогда ранее не публиковалось; окончательную валидацию выполняет реальный `videos.update` на стороне YouTube.

## Проверка статуса (`WaitProcessing`)

- Завершение загрузки (`uploadStatus=uploaded`) не считается успешной обработкой.
- `WaitProcessing` ожидает `processingDetails.processingStatus == "succeeded"` и немедленно возвращает детальную ошибку при `processingStatus` `failed` / `terminated` или `uploadStatus` `rejected` / `failed`, ограничивая реальное ожидание и HTTP-запросы переданным `timeout`.
