# ADR 0002: Машина состояний как единственная точка изменения VideoJob

- Статус: принято
- Дата: 2026-11-12
- Этап: TASK 001

## Контекст

Публикация без валидации, пропуск монтажа или двойная публикация одного
видео — необратимые внешние эффекты. Будущий Temporal-workflow будет
переигрывать историю и повторять activity, поэтому правила должны быть в
домене, а не в оркестраторе.

## Решение

1. `VideoJob` хранит состояние в неэкспортируемом поле; изменить его можно
   только через `Transition(to, at)`.
2. Разрешённые переходы заданы статической таблицей `transitions`; любая пара
   вне таблицы даёт `ErrInvalidTransition`, переход в текущее состояние —
   `ErrSameState`.
3. Предусловия проверяются в `guard`:
   - `VALIDATED` требует записанного `VideoValidation` с `Passed: true`;
   - `UPLOADED` требует пройденной валидации;
   - `SCHEDULED` и `PUBLISHED` требуют привязанной `Publication`.
4. `RETRY_PENDING` не имеет статических целей: переход возможен только в
   `ResumeState`, который запоминается при входе в состояние повтора.
5. `FAILED` сохраняет `ResumeState`, поэтому повтор продолжает с упавшего шага,
   а не с начала и не с пропуском.
6. Лимит попыток проверяется при входе в `RETRY_PENDING`
   (`ErrRetriesExhausted`).
7. Время перехода передаётся параметром: домен не читает системные часы, что
   делает тесты и будущий replay детерминированными.

## Последствия

- Невозможно опубликовать невалидированное видео или дважды опубликовать
  одно задание.
- Состояние всегда сопровождается отметкой времени (`ValidatedAt`,
  `UploadedAt`, `ScheduledAt`, `PublishedAt`).
- Восстановление после сбоя описано данными (`ResumeState`, `Attempts`), а не
  кодом воркфлоу.

## Альтернативы

- **Строковое поле `status` с проверками в сервисах.** Правила расползлись бы
  по вызывающему коду.
- **Отдельный пакет `statemachine`.** Лишний слой: состояний немного, они
  принадлежат агрегату.
